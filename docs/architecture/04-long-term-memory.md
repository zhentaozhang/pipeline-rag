# 主题四：Summary Compression 长期记忆 —— 面试深挖分析

> **演进状态**：✅ 有效（2026-08 核对）。摘要压缩记忆基础上新增 Mem0 式用户事实记忆（user_key 用户级维度 + RAG/Agent 注入，见演进记录 009/011）；响应缓存仅缓存无历史确定性问答（006）。

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
这是一个知识库问答系统，用户会**持续追问**："第 3 步怎么配？"→"那如果环境是内网呢？"→"刚才说的那个参数呢？"——一轮对话几十轮很常见。系统必须"记住"之前说过什么：
- **连续性**：用户说"那它呢"，模型要懂"它"指代的是上一轮讨论的对象；
- **长程一致性**：第 30 轮的问题，要能复用第 2 轮确认过的事实，不能前后矛盾；
- **不被早期信息带偏**：用户中途修正过结论（"其实不是这样"），后面要按新结论回答。

### 原来的方案有什么问题
"把全部历史塞给模型"是不行的：
- **上下文窗口有上限**：几十轮原文轻松超出窗口，模型直接拒绝/截断；
- **费用随长度线性涨**：历史越长，每次请求的 token 费越高；
- **信息稀释**：海量历史里模型抓不住"用户到底在干什么、已经确认了什么"。

### 为什么需要重新设计
需要一个记忆方案满足四个约束：
1. **成本有界**：记忆体量不能随轮数无限增长；
2. **近的有细节**：最近几轮要保留原文，因为指代消解依赖细节；
3. **远的别丢**：早期事实要保留（压缩成摘要），不能一截了之；
4. **别写坏**：压缩在后台异步跑，多任务并发时不能互相覆盖、摘要不能倒退。

> 一句话背景叙述（面试开场用）：
> "长会话把全部历史塞给模型会爆窗口、还贵。我们做了双轨记忆：最近 4 轮保留原文（管连续性），更早的历史异步压缩成一份结构化摘要（管长程一致性）。压缩不是全量重写，而是每次只把'掉出窗口'的最旧一批合入已有摘要，体量恒定。因为压缩是异步的，并发写会互相覆盖，所以我们用'游标 + 版本号 CAS'双保险保证摘要只前进、不倒退。这套方案支持 50+ 轮会话不丢事实。"

## 2. 整体架构

### 记忆双轨 + 异步压缩链路
```
[写入侧]（每轮回答完成后）
  落库本轮问答（exchange）
    → 触发异步压缩任务（Celery，不阻塞响应）
        → 取出"已压缩游标之后"的新增轮次
        → 筛出超出窗口的最旧批次（每次最多 summary_batch_size=6 轮）
        → LLM 把该批合并进已有结构化摘要（失败降级为规则合并）
        → 游标前移 + 版本号 +1（CAS 写入）

[读取侧]（每轮回答前）
  加载 ConversationMemory（结构化摘要 + 游标/压缩次数）
  加载最近 window_size=4 轮原文
  组装：长期摘要（早期事实）+ 最近原文（近期细节）→ 注入上下文
```

### 结构化摘要字段（长期记忆的载体）
```
ConversationSummaryPayload
  summary              长期会话摘要（正文，上限 1400 字）
  conversationGoal     会话目标
  stableFacts          已确认事实（列表，去重 + 限条数）
  userPreferences      用户偏好与约束
  resolvedPoints       已解决问题
  pendingQuestions     待跟进问题
  retrievalHints       检索提示（历史里出现过的专有名词/主题）
```

### 关键参数（可引用，均为配置项）
```
strategy = summary_compression    # 默认记忆策略
window_size = 4                   # 最近 N 轮保留原文
summary_batch_size = 6            # 每次最多推进多少轮进摘要
max_summary_chars = 1400          # 长期摘要字符上限
max_window_chars = 2200           # 最近原文渲染上限
max_section_items = 6             # 每个字段最多保留条数
max_item_length = 80              # 单条内容截断
```

### 架构核心：成本与轮数解耦 + 异步一致性
- **成本有界**：长期摘要固定上限，最近窗口固定轮数——喂给模型的记忆体量与对话轮数**解耦**；
- **增量推进**：只压"掉出窗口"的最旧轮次，不每轮全量重写；
- **一致性**：游标（covered_exchange_id）只允许向前 + 版本号 CAS 原子写入，并发下摘要单调前进。

> 架构叙述锚点：
> "记忆分两条轨：一条管近（窗口原文），一条管长（结构化摘要）。压缩是'增量 + 异步'的——每轮回答完在后台把最旧的一小批合进摘要，在线路径完全不被拖累。因为异步会并发，所以写入用版本 CAS：只有基于最新版本的写入才生效，后提交者自动失效，摘要永不倒退。"

## 3. 核心技术方案拆解

### 技术点 A：为什么"窗口原文 + 结构化摘要"双轨

**是什么**：短期轨保留最近 `window_size=4` 轮原文（渲染成对话记录）；长期轨把更早历史压缩成结构化摘要；回答时两者拼在一起喂给模型。

**为什么**：
- **窗口管"近"**：指代消解（"那它呢"）依赖最近几轮的**原文细节**，摘要会丢细节；
- **摘要管"长"**：第 30 轮要复用第 2 轮的事实，窗口早被挤掉，只能靠摘要；
- 双轨互补：**用摘要兜住"长"，用窗口兜住"近"**。

**为什么不用其他方案**：
- 只用窗口：超过窗口的历史全丢，长程一致性做不到；
- 只用摘要：连续追问的指代细节丢失，且摘要压缩本质是信息损耗，只压近期也浪费；
- 全量历史塞 prompt：成本随轮数线性涨、超窗口、信息稀释。

**风险**：双轨拼接可能产生重复或冲突（摘要说过 + 窗口又出现）。
**优化**：组装时摘要在前、窗口在后；结构化字段（stableFacts）让"已确认事实"与近期对话有明确边界。

---

### 技术点 B：为什么摘要要"结构化字段"，而不是一段自由文本

**是什么**：摘要不是一段散文，而是带固定槽位的结构化数据（目标/事实/偏好/已解决/待跟进/检索提示）。

**为什么**：摘要的消费方不只是"回答"，还有**规划**——
- 回答时读"摘要 + 已确认事实"，避免与用户已确认的结论冲突；
- 检索时读"检索提示"，把历史里的专有名词喂给检索（衔接主题三）；
- 规划时读"会话目标/待跟进"，知道对话在朝什么方向推进。
字段化之后**各环节各取所需**，且天然支持去重、数量上限控制。

**为什么不用其他方案**：
- 自由文本摘要：信息挤在散文里，消费方要从一段话里硬找字段，且无结构约束容易越写越散；
- 向量记忆（MemGPT 式）：把历史做向量索引、按相关性召回——适合"在庞大历史里找特定片段"，但我们的场景是"整体记住关键事实 + 近期细节"，结构化摘要更省、更稳。

**风险**：字段边界不清晰时 LLM 可能塞错槽位。
**优化**：LLM 输出要求 JSON 严格匹配结构；解析失败降级为把原文塞进 summary 字段（不丢数据）。

---

### 技术点 C：为什么"增量压缩"而不是每次全量重写

**是什么**：压缩只处理"掉出窗口的最旧批次"（`_select_overflow_batches` 筛选），每次最多推进 `summary_batch_size=6` 轮，把该批合入已有摘要。

**为什么**：
- **成本恒定**：全量重写每次要把"全部历史 + 新对话"再喂一次 LLM，随轮数线性涨；增量只喂"已有摘要 + 最新一批"，体量基本恒定；
- **稳定性**：全量重写有"重写后丢旧事实"的风险（LLM 压缩本质是信息损耗）；增量每次只合入一小批，改动小、可追溯；
- **窗口优先**：窗口内的轮次保留原文，只有**超出窗口**的才进摘要——近期永远有最准的原文可用。

**为什么不用其他方案**：
- 全量重写：成本线性涨、易丢事实、每次结果还不稳定；
- 只压一次（摘要不再更新）：早期对话后续变化（用户修正结论）无法反映进摘要。

**风险**：增量合并时 LLM 可能"忘记"摘要里已有的事实。
**优化**：合并 prompt 同时给"当前摘要 + 新对话批"，要求按结构输出完整新摘要；规则降级路径保证至少不丢原文片段。

---

### 技术点 D：为什么压缩必须异步（Celery），而不是同步

**是什么**：每轮回答完成后，`save` 只负责落库 + 投递一个 Celery 异步任务 `task_compress_conversation_memory`，压缩在后台执行，不阻塞响应返回。

**为什么**：
- 压缩是一次 LLM 调用，可能几秒；放在回答路径里会**直接拉长响应延迟**；
- 记忆刷新不需要用户等待——本轮回答已返回，摘要晚几秒更新无感知；
- 后台任务还可**批量**处理（一次合并 6 轮），效率高于每轮同步压。

**为什么不用其他方案**：
- 同步压缩：每次回答 + 几秒压缩延迟，在线体验劣化；
- 靠定时全量重算：不用触发时机，压得慢、压得糙。

**风险**：异步引入并发写问题（见技术点 E）；任务失败需要重试。
**优化**：Celery 任务带 max_retries=3；失败有日志，下次触发会基于最新游标重试。

---

### 技术点 E：异步并发下怎么保证"摘要不倒退"（本主题最深点）

**是什么**：写入用**双保险**——
1. **游标（covered_exchange_id）**：摘要记录"已压缩到第几轮"。写前重读最新游标，若别的任务已写得更远，本次直接放弃（别人已写好，不需要再写）；
2. **版本号 CAS**：写入用条件更新 `WHERE summary_version = 期望版本`，版本没变才写，成功后版本 +1；并发时后提交者 `rowcount=0` 自动失效。

**为什么**：
- 异步任务会并发（同一会话多次触发、多 worker 同时消费），没有保护会出现：两个任务都读到旧摘要 → 各自合并 → 后写者覆盖先写者 → **前面合并的内容丢失（摘要倒退）**；
- 游标检查处理"重复劳动"（写得更远就跳过），CAS 处理"写冲突"（版本不符就失效）——两道防线互相补充；
- 目的：**摘要单调前进，绝不回退**。

**为什么不用其他方案**：
- 加分布式锁串行化：同一会话的压缩串行执行，简单但增加锁依赖和排队延迟；
- 乐观锁（CAS）单独用：能挡写冲突，但挡不住"两个任务基于同一版本各自合并出一份都对、但互相丢更新"的重复劳动——需要游标先判断"是不是别人已经做过"。

**风险**：CAS 冲突时任务静默跳过，可能延迟压缩进度。
**优化**：跳过有日志；下次触发（新一轮对话）会带着更新游标重试，进度不丢。

---

### 技术点 F：压缩失败 / LLM 输出异常怎么办

**是什么**：合并摘要时的三级降级——
1. 优先要求 LLM 输出结构化 JSON；
2. 失败则去掉 JSON 格式约束重试一次；
3. 仍失败则**规则式合并**：把新批次的问答按模板拼进摘要、做去重和长度截断，至少不丢原文片段。

**为什么**：LLM 是软依赖，压缩任务不能因为 LLM 不稳定就丢数据——规则合并是"最朴素但可靠"的保底。

**风险**：规则合并质量差（不如 LLM 理解语义）。
**优化**：正常路径是 LLM 合并，规则合并只在异常时触发，且有日志可查。

---

### 技术点 G：记忆方案如何验证效果 / 排查坏 case

**是什么**：每个会话可查到记忆状态——是否有长期摘要、覆盖到第几轮、压缩次数、最近窗口保留几轮原文；回答前注入的记忆内容全程留痕。

**为什么**：遇到"该记住的没记住"的坏 case，必须能定位是哪一环的问题：
- 是摘要丢了？（看覆盖游标、压缩次数）
- 是窗口被挤掉？（看窗口轮数）
- 是根本没触发压缩？（看任务日志）
- 还是检索没带提示？（看 retrievalHints）

**优化**：可**全量重建摘要**（删除后重压），作为"怀疑摘要坏了"时的修复手段；可**删除会话记忆**，应对用户"忘了之前的约定"。

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"为什么双轨"出发
- **第一层**：为什么不用把全部历史塞给模型？
  - 答：窗口有上限、费用线性涨、信息稀释。
- **第二层**：为什么是"窗口原文 + 结构化摘要"这个组合？
  - 答：窗口管近（指代消解要原文细节），摘要管长（早期事实不丢），互补。
- **第三层**：只留窗口、超出的直接丢行不行？
  - 答：不行。第 30 轮要复用第 2 轮的事实，丢了就前后矛盾。摘要就是为"远但重要"的事实兜底。

### 追问链 2：从"为什么结构化摘要"出发
- **第一层**：摘要为什么不是一段话？
  - 答：因为消费方不只回答，还要检索提示、规划目标，字段化才能各取所需。
- **第二层**：为什么不干脆用向量记忆（MemGPT 式）？
  - 答：向量记忆适合"在庞大历史里按相关性找片段"，但我们的场景是"整体记住关键事实 + 近期细节"，结构化摘要更省、更稳、可控性更强。
- **第三层**：字段塞错了怎么办？
  - 答：要求 LLM 输出严格 JSON；解析失败降级为塞进 summary 字段，不丢数据。

### 追问链 3：从"异步并发"出发
- **第一层**：压缩为什么要异步？
  - 答：压缩是 LLM 调用，同步会拉长响应延迟；后台跑用户无感知。
- **第二层**：异步了，两个任务并发会不会写坏摘要？
  - 答：会，所以用游标 + 版本 CAS 双保险。
- **第三层**：具体怎么防"摘要倒退"？
  - 答：游标判断"别人是否已写得更远"（防重复劳动），CAS 判断"版本是否已被改"（防写冲突），两道防线让并发下只有写得最全的生效，摘要单调前进。

### 追问链 4：从"记忆成本"出发
- **第一层**：长会话 token 会不会失控？
  - 答：不会。长期摘要固定上限（1400 字），最近窗口固定轮数（4 轮），喂给模型的记忆体量与轮数解耦。
- **第二层**：那摘要越压越粗，事实会不会丢？
  - 答：结构化字段降低丢失概率（事实进 stableFacts，问题进 pendingQuestions，各占槽位）；还有全量重建能力作修复。
- **第三层**：用户中途改主意（"其实不是这样"），摘要能跟上吗？
  - 答：增量压缩持续推进，新轮次合入时模型会看到最新结论；已解决/待跟进字段会反映状态变化。这是结构化的好处。

## 5. 极端情况处理（怎么办层汇总）

| 场景 | 怎么办 |
|------|--------|
| LLM 摘要合并失败 | 去掉 JSON 约束重试一次，再失败降级为规则合并（不丢原文片段） |
| 摘要 JSON 解析失败 | 降级为把原文塞进 summary 字段，不丢数据 |
| 多任务并发写冲突 | 游标检查 + 版本 CAS 双保险；后提交者自动失效，摘要不倒退 |
| 压缩任务失败 | Celery max_retries=3；下次触发基于最新游标重试 |
| 摘要越压越不准 | 结构化字段兜底 + 可全量重建摘要 |
| 用户要"忘了之前的约定" | 删除会话记忆，从干净状态重新开始 |
| 记忆没生效（该记住的没记住） | 查摘要游标/压缩次数/窗口轮数/任务日志，定位是哪一环 |
| 窗口被挤掉重要上下文 | 窗口轮数可配置，需要更大上下文可调大 window_size |
| 摘要与窗口内容冲突 | 组装时摘要在前、窗口在后；字段化明确"已确认事实"边界 |

## 附：面试前必查的隐患

| 隐患 | 说明 | 应对 |
|---|---|---|
| "50+ 轮会话"口径 | 简历数字需可支撑 | 想清楚支撑点：记忆体量有界（1400 字 + 4 轮），轮数再多成本也不涨；"记忆一致性"靠游标 + CAS。面试说清机制即可，不必硬扯压测报告 |
