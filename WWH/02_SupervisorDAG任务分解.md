# 主题二：Supervisor + DAG 任务分解 —— 面试深挖分析

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
用户的问题不全是"一个检索能答完"的。常见两类复合问题：
- **对比型**："对比 A 和 B 的接入流程，并说明各自的前置条件"；
- **推导型**："先查 A 的定义，再结合它评估我们的方案是否满足"。

这类问题拆成几个子问题各自解决，比一个大 prompt 硬答质量更高、也更快。

### 原来的方案有什么问题
在主题一的基础上，单路径执行无法覆盖复合问题：
- **一次检索答不全**：复合问题混在一个检索里，各子问题的证据互相稀释，召回质量下降；
- **串行低效**：如果人为拆几步串行跑，总耗时是各步之和；
- **无法复用**：不同复合问题的拆法没有固定模板，写死规则只能覆盖已知场景。

### 为什么需要重新设计
需要一个**能泛化到未见问题结构**的分解机制，同时保证分解结果可靠、执行高效：
- 用 LLM 做分解（泛化），但 LLM 输出不可信 → 用**结构校验 + 质量评审**双重兜底；
- 子任务之间有依赖 → 用**DAG**表达，**拓扑分层**决定并行度；
- 能并行的并行、必须等的才等，总耗时 ≈ 最长依赖链。

> 一句话背景叙述（面试开场用）：
> "单条检索路径处理不了复合问题——比如'对比 A 和 B 的接入流程'，混在一个检索里证据互相稀释。我们加了一层 Supervisor：用 LLM 把复杂问题自动分解成带依赖关系的子任务，每个子任务单独走执行器，再按依赖做拓扑分层并行执行，最后综合成一份完整回答。核心是两层保险——LLM 负责泛化拆解，规则校验 + 质量评审负责控风险，拆得不好宁可回退成单路径，也绝不让坏计划上线。"

## 2. 整体架构

### 分解与执行链路
```
复合问题（已过主题一编排）
  │
  ▼
[Supervisor 分解]
  LLM 分解 → 子任务列表（每个带 mode / question / depends_on 依赖）
  │
  ▼
[结构校验]（纯规则，不花 LLM）
  ID 唯一 / 问题非空 / 依赖必须指向真实存在的子任务
  │ 不通过 → 放弃多智能体，回退单路径
  ▼
[质量评审]（第二个 LLM 再审）
  分解是否完整、子任务是否重复/遗漏
  │ 不通过 → 把评审反馈喂回分解 LLM，重新分解（有重试上限）
  ▼
[拓扑分层]（Kahn 算法）
  无依赖 → 第 1 层；只依赖第 1 层 → 第 2 层……
  │
  ▼
[层内并行执行]（asyncio.gather）
  每层内子任务同时跑，层间串行等待
  │
  ▼
[综合]（Aggregator）
  所有子结果交给综合 LLM → 一份连贯回答（引用去重合并）
```

### 关键数据流
```
ExecutionPlan（supervisor_mode=true）
  └─ sub_plans: [SubPlan(id, mode, question, depends_on=[...]), ...]
       └─ 拓扑分层后：layers = [[无依赖], [只依赖第1层], ...]
            └─ 每层 asyncio.gather 并行 → WorkerResult 列表
                 └─ Aggregator 综合 → 流式 SSE 输出 + 引用合并
```

### 架构核心：为什么分解要"先决后防"
- **决**：是否分解、怎么拆，由 LLM 决定——它甚至可以拒绝分解（输出 `decompose: false`），简单问题保持单路径；
- **防**：LLM 拆完必须过两道校验，任何一环不过就回退；
- 这套"LLM 泛化 + 规则/评审兜底"是本主题的设计主线。

> 架构叙述锚点：
> "Supervisor 是主题一编排的后处理，不在 10 个 Stage 内。它负责把已经确认的复合问题拆成带依赖的子计划，然后在执行层用拓扑分层 + 异步并发跑起来。整个链路里有两个模型角色：一个是分解者，一个是评审者——评审不通过会把意见带回去重新拆。"

## 3. 核心技术方案拆解

### 技术点 A：为什么用 LLM 分解（而不是写死规则）

**是什么**：把复合问题交给 LLM，要求输出一组子计划，每个子计划带执行模式、子问题、以及依赖声明。

**为什么**：
- 复合问题的拆法**没有固定模板**——"对比 A/B"和"查 A 再给建议"结构完全不同，规则只能覆盖已知场景；
- LLM 能泛化到未见过的问题结构；
- 同时让 LLM 判断"值不值得拆"（输出 `decompose: false` 即拒绝），把成本决策交给模型而不是默认全拆。

**为什么不用其他方案**：
- 写死规则：只能覆盖枚举过的场景，问题一变就失效；
- 全拆默认：简单问题也走多智能体，白白增加 LLM 开销和延迟。

**风险**：LLM 输出不可信——可能拆错、拆漏、依赖悬空。
**优化**：输出不信任，校验兜底（见技术点 B）。

---

### 技术点 B：两道校验兜底 —— 结构校验 + 质量评审

**是什么**：LLM 拆完先过两道关卡：
1. **结构校验**（纯规则，零 LLM 成本）：子计划 ID 不能重复、问题不能为空、依赖引用必须指向真实存在的子计划；
2. **质量评审**（第二个 LLM）：看分解是否完整、子任务是否重复/遗漏，输出通过或不通过 + 反馈。

**为什么**：
- 结构校验拦截**硬错误**（依赖悬空、ID 重复），这些是程序能确定的，不必花 LLM；
- 质量评审拦截**软问题**（拆得不好），把反馈**喂回分解 LLM**重新拆，最多重试若干次；
- 用最便宜的手段拦最多的问题：规则拦结构，LLM 拦质量。

**为什么不用其他方案**：
- 只靠结构校验：拦不住"拆得不对但结构合法"；
- 只靠质量评审：硬错误也要花 LLM，且评审对结构错误不可靠。

**风险**：评审本身也是 LLM，可能误判。
**优化**：评审失败时兜底放行（不因评审问题阻塞主链路）；重试耗尽即回退单路径。

---

### 技术点 C：LangGraph 图 + 手写循环双实现

**是什么**：分解 + 校验 + 评审 + 重试，有两条实现路径：
1. **LangGraph 版**：`decompose → validate → review` 三个节点组成状态图，循环由框架控制，失败走条件边回到 decompose；
2. **手写循环版**：等价逻辑用代码循环实现，作为回退。

**为什么双实现**：
- LangGraph 版让"分解→评审→重拆"的循环结构**显式化**、状态由框架持有，代码更干净、可注入确定性测试；
- 手写版保证**框架不可用 / 异常时功能不回退**；
- 主路径优先走图，图运行但判定不合格 → 直接保持单路径；图异常 → 回退手写版。语义保持一致（重试上限一致），避免两套逻辑结果漂移。

**为什么不用其他方案**：
- 只用手写循环：循环控制散在业务代码里，状态维护手写；
- 只用 LangGraph：多一个运行时依赖，异常处理要额外兜底。

**风险**：两套实现并行，逻辑可能漂移。
**优化**：复用同一套"构建子计划 / 结构校验"纯函数，图与手写版共享，漂移面最小。

---

### 技术点 D：拓扑分层 + 层内并行

**是什么**：拿到带依赖的子计划后，做一次拓扑分层（Kahn 算法）：无依赖的子任务放第 1 层，只依赖第 1 层的放第 2 层……每层内部用 `asyncio.gather` 并行执行，层与层串行等待。

**为什么**：
- 子任务间有**真实依赖**（查"接入流程"前要先知道"A 是什么"）；
- 全并行：依赖方拿到空输入；全串行：无关任务白白排队；
- 拓扑分层卡在中间：**能并行的并行、必须等的才等**，总耗时 ≈ 最长依赖链，而不是子任务耗时之和。

**为什么不用其他方案**：
- 全并行：无视依赖，结果错误；
- 人工指定层：每类问题写死，无法泛化。

**风险**：出现循环依赖时拓扑算法无法分层。
**优化**：分层前检测——层数统计不等于子计划总数即判定"循环依赖或孤立节点"，放弃并行、给出提示。

---

### 技术点 E：综合（Aggregator）—— 多源结果怎么合成一份回答

**是什么**：所有子任务完成后，把各 WorkerResult 交给一个综合 LLM，让它把多份局部答案组织成一份连贯的完整回答；引用列表去重合并。

**为什么**：
- 每个子任务只产出自己视角的答案，直接拼接不成文；
- 综合 LLM 负责去重、组织顺序、消除冲突；
- 引用合并是必要的：同一证据被多个子任务引用时只保留一份。

**为什么不用其他方案**：
- 简单拼接：可能重复、冲突、不成文；
- 不做综合（直接分点返回）：对用户不友好，且引用会重复。

**风险**：综合 LLM 失败。
**优化**：失败降级为**按顺序拼接**各子结果（保留模式标签），保证有输出；所有子任务都失败时给明确失败说明，不返回空回答。

---

### 技术点 F：执行中的失败处理

**是什么**：每个子任务在进程内被独立保护，失败只影响自己。

**为什么**：
- 不中断同层其他并行任务；
- 综合阶段跳过无结果/出错的子任务，只综合有效结果；
- 极端情况（全部失败）时综合器给出明确失败说明而不是空回答。

**风险**：子任务失败导致答案缺一块，用户不知道。
**优化**：每个子任务执行结果带"成功/失败 + 错误信息"，思考过程流式可见，用户能看到"哪个子任务失败了"。

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"为什么分解还要评审"出发
- **第一层**：LLM 拆完为什么不直接用？
  - 答：LLM 输出不可信，可能拆错、拆漏、依赖悬空。先过纯规则结构校验拦硬错误。
- **第二层**：结构校验过了就够吗？
  - 答：不够，结构合法不等于拆得好。再用第二个 LLM 做质量评审，看完整性和重复性。
- **第三层**：评审不通过呢？会不会一直重拆？
  - 答：不会无限重试。评审反馈会带回去重新分解，但有重试上限；重试耗尽直接回退单路径执行，宁可少拆不拆错。

### 追问链 2：从"为什么拓扑分层"出发
- **第一层**：为什么不是把所有子任务一次全并行？
  - 答：子任务之间有真实依赖，全并行依赖方拿到空输入。
- **第二层**：为什么不是全串行？
  - 答：浪费了无关子任务的并行机会，总耗时变成子任务耗时之和。
- **第三层**：拓扑分层最坏情况是什么？
  - 答：遇到循环依赖无法分层——检测到层数统计不等于子计划总数就放弃并行、给出提示，不会死循环或静默错跑。

### 追问链 3：从"两个模型角色"出发
- **第一层**：分解和评审是同一个模型吗？
  - 答：是同一个模型的两个角色（分解者/评审者），通过不同的 prompt 扮演。
- **第二层**：同一个模型自己拆自己审，会不会永远通过？
  - 答：会存在这个风险，所以评审有兜底——评审失败/异常时放行（不阻塞主链路），评审不通过有重试上限，且结构校验是独立于 LLM 的纯规则，不受"自己审自己"影响。
- **第三层**：多智能体会不会比单路径更贵？
  - 答：会，分解 + 评审 + 每个子任务 + 综合，LLM 调用数明显更多。所以默认不拆：LLM 输出 `decompose: false` 时保持单路径，只有确实值得拆的复合问题才走多智能体，成本决策交给模型。

### 追问链 4：从"双实现"出发
- **第一层**：LangGraph 版和手写版是什么关系？
  - 答：同一逻辑的两条实现，LangGraph 版优先，异常时回退手写版。
- **第二层**：为什么要维护两套？
  - 答：LangGraph 让"分解→评审→重拆"循环显式化、状态由框架持有；手写版保证框架不可用时功能不挂。
- **第三层**：两套会不会行为不一致？
  - 答：共享同一套"构建子计划/结构校验"纯函数，重试上限语义一致；图判定不合格时直接保持单路径，不重跑手写版，避免二次 LLM 成本和结果不确定性。

## 5. 极端情况处理（怎么办层汇总）

| 场景 | 怎么办 |
|------|--------|
| LLM 分解输出非法 JSON / 调用失败 | 返回空计划，保持单路径执行，不中断对话 |
| 结构校验不通过（依赖悬空/ID 重复/问题为空） | 直接放弃多智能体，回退单路径 |
| 质量评审不通过 | 反馈带回重新分解，有重试上限；耗尽回退单路径 |
| 评审 LLM 调用失败/异常 | 兜底放行（按通过处理），不阻塞主链路 |
| 子计划存在循环依赖或孤立节点 | 拓扑分层检测到总数不符 → 放弃并行、给出提示 |
| 单个子任务执行失败/超时 | 独立保护，不中断同层其他任务；综合阶段跳过失败结果 |
| 所有子任务都失败 | 综合器给出明确失败说明，不返回空回答 |
| 综合 LLM 失败 | 降级为按顺序拼接各子结果（保留模式标签） |
| 简单问题被强行分解 | LLM 默认输出 `decompose: false` 保持单路径，成本决策交给模型 |
| LangGraph 框架不可用 | 回退手写循环版，功能不降级 |

## 附：面试前必查的隐患

| 隐患 | 说明 | 应对 |
|---|---|---|
| Supervisor 与主题一的关系 | Supervisor 是编排收尾的 **post-processing**，不在 10 个 Stage 内 | 别把 Supervisor 说成"第 11 个 Stage"；它是主题一的后续层，负责复合问题 |
| 两个模型角色容易穿帮 | 分解者和评审者是同一个模型的两个 prompt 角色 | 主动说明"同模型分角色 + 评审有兜底放行"，比被问到时才解释更可信 |
| 多智能体的成本问题 | LLM 调用数明显多于单路径 | 必须主动讲"默认不拆 + `decompose: false` 拒绝机制"，否则面试官会质疑为什么不用单路径 |
| 子任务与引用 | 每个子任务会产生自己的引用，综合时要去重合并 | 讲清"证据去重 + 引用合并"在综合层做，避免重复引用 |
