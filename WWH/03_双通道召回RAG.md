# 主题三：PGVector + Elasticsearch 双通道召回 —— 面试深挖分析

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
这是企业内部知识库问答系统的**检索核心**。文档（手册、流程、政策、规范）入库后被切块、向量化、双份落库；用户提问时，系统要在海量文档块里找到"真正回答这个问题的证据片段"，再交给 LLM 生成回答。

回答质量的根基在检索——**证据找错了，后面的生成再强也没用**。

### 原来的方案有什么问题
如果只用单通道（纯向量或纯关键词），各有硬伤：
- **纯向量检索**：强在语义匹配（"意思相同、用词不同"能召回），但企业文档里有大量**精确信息**——产品型号（R6.2）、流程编号（第 3 步）、专有名词、代码片段，这类词向量容易淹没在语义里；
- **纯关键词检索**：强在精确命中，但**同义改写**（"部署" vs "安装"、"故障" vs "异常"）命中不了，语义近似的表达召回为 0。

### 为什么需要重新设计
需要两条通道**互补**：语义靠向量、精确靠关键词，再通过融合把两路结果合并，用重排把最相关的证据挑到最前。同时要解决：
- 两路分数量纲不同，**不能直接比较**（融合问题）；
- 切块粒度"命中精准"与"上下文完整"的矛盾（粒度问题）；
- 找对证据不代表"按当前问题排对了序"（排序问题）。

> 一句话背景叙述（面试开场用）：
> "企业内部文档里有大量产品型号、流程编号这类精确信息，纯向量检索会丢，纯关键词又接不住同义表达。所以我们做了双通道召回：PGVector 负责语义、Elasticsearch 负责精确匹配，两路并行检索后先用 RRF 融合（解决分数量纲不可比），再做 Parent-Child 提升（解决小块命中但上下文不完整），最后上一个可配置的 Rerank 做语义精排。整个链路每一步都留痕，坏 case 能精确查到卡在哪一步。这个方案把 Top-5 召回准确率从纯向量的 72% 提到了 91%。"

## 2. 整体架构

### 全链路拓扑（离线入库 → 在线检索）
```
[离线入库]                                    [在线 Query]
文档解析
  → 结构化/递归/语义切块                       查询处理（改写/拆子问题/加过滤条件）
      Parent 块（大块：上下文）                     │
      └─ Child 块（小块：命中粒度）                 ▼
  → 仅 Child 块向量化                       双通道并行检索（各带超时保护）
      │                                        向量路 PGVector（余弦相似度）
  → 双份落库                                   关键词路 ES（BM25 + 字段加权）
      PGVector（embedding）                     │ 证据闸门（各自滤低质命中）
      ES（chunkText/sectionPath 等）            ▼
                                              RRF 融合（按排名合并）
                                                ▼
                                              Parent-Child 提升（小块→大块）
                                                ▼
                                              Rerank 精排（可配置，失败降级跳过）
                                                ▼
                                              Prompt 组装（预算控制）→ LLM 生成
```

### 关键参数（可引用，均为配置项）
```
vector_top_k = 5        keyword_top_k = 5        # 两路各自召回
candidate_top_k = 6     final_top_k = 5          # 融合后候选 / 最终进 Prompt
min_vector_similarity = 0.55                     # 向量证据闸门阈值
keyword_score_ratio = 0.35                       # 关键词闸门：最低 = 最高分 × 0.35
channel_timeout_ms = 5000                        # 单通道超时（降级不影响另一路）
sub_question_timeout_ms = 12000                  # 单子问题检索超时
corrective_retrieval_max_rounds = 1              # 证据不足自动重查轮数
parent_evidence_max_chars = 2200                 # Parent 块最大入 Prompt 长度
chunk: recursive 800 字 / overlap 120            # 递归切块粒度
```

### 架构核心：召回靠广、精排靠准
- **召回阶段**（双通道 + 融合）**宁多勿漏**：两路并行，各自召回后再合并，保证该有的证据都在候选里；
- **精排阶段**（Rerank + topk）**才做减法**：用专用重排模型把真正相关的挑到最前，截断到最终条数；
- 证据不足时还有一层纠错（改写重查），兜住"第一轮没查对"。

> 架构叙述锚点：
> "检索分两段想问题：先把候选捞全（召回），再按当前问题排准（精排）。召回靠双通道互补，精排靠 Rerank。捞不全后面白搭，排不准前面白做。"

## 3. 核心技术方案拆解

### 技术点 A：为什么双通道（向量 + 关键词），而不是只用向量

**是什么**：向量路（PGVector 余弦相似度）与关键词路（ES BM25 + 字段加权）并行检索。

**为什么**：
- 两类信息特性不同：**语义近似**（同义改写）靠向量，**精确匹配**（型号、编号、专有名词）靠关键词；
- 企业文档精确信息密集，纯向量会漏；纯关键词接不住同义表达；
- 两路互补是"召回率从 72% → 91%"的主要来源。

**为什么不用其他方案**：
- 只用向量：漏精确匹配；
- 只用关键词：漏语义近似；
- 先向量后关键词（串行）：如果第一路就决定结果，第二路永远来不及补救；并行才能两路都捞全。

**风险**：两路都召回 = 候选更多，噪音更多。
**优化**：证据闸门先各自过滤，融合后再重排，把噪音压下去。

---

### 技术点 B：为什么向量存 PGVector（而不是 Milvus / Qdrant / FAISS）

**是什么**：向量检索直接用 asyncpg 查 `pipeline_rag_document_embedding` 表，基于 cosine similarity 排序。

**为什么**：
- 向量 + 结构化过滤一体化：检索常带过滤条件（租户、文档 ID、章节、年份、文档名）——SQL 里 `WHERE tenant_id=? AND document_id=ANY(?)` 和 `ORDER BY embedding <=> ?` 直接写在一条查询里，**不需要单独维护"向量库 + 元数据库"两套再 join**；
- 数据同源：文档的块、元数据、向量都在同一套 PostgreSQL 体系，入库时用 UPSERT 保证幂等，重跑不累积；
- 省一个中间件：规模在这个量级时，专用向量库的增益不抵多维护一个组件的成本。

**为什么不用其他方案**：
- **Milvus/Qdrant**：纯向量库强在亿级向量、高 QPS 检索，但我们的量级用不上；且"向量 + 过滤 + 元数据"要跨库 join，反而更复杂；
- **FAISS**：内存型、单机，无持久化和过滤能力，需要自己搭管理；
- 结论：**规模决定选型**——量上来、过滤复杂化后再迁移专用向量库，接口已隔离（走 provider），可替换。

**风险**：向量库和关系库共用实例，量大可能互相影响。
**优化**：向量表单独放在 PG 实例（代码里 PG 与业务 MySQL 分离），避免挤占业务库。

---

### 技术点 C：为什么关键词用 ES（而不是 PG 全文检索 / 只靠向量）

**是什么**：ES 存 chunkText、sectionPath、documentName、knowledgeScopeName 等字段，用 BM25 + 字段加权召回。

**为什么**：
- 需要**字段级加权**：章节路径（sectionPath）权重最高（boost 6~8），文档名次之，正文最低——因为"问题提到章节名"时，命中章节路径远比命中正文有效；
- 需要**精确短语/通配**能力：match_phrase、wildcard 处理"第 X 步"这类结构化查询；
- 文档结构信息（章节、条目序号）要能单独检索。

**为什么不用其他方案**：
- PG 全文检索：能做基础分词，但字段加权、短语、通配的灵活度不如 ES，且要额外维护中文分词；
- 只用向量：见技术点 A，精确匹配是硬伤。

**风险**：ES 挂掉整个关键词路断掉。
**优化**：ES 失败自动降级为 PG 内关键词模糊匹配（LIKE + 加权得分），保证关键词路不因 ES 宕机完全失效；单通道超时 5s 内降级，不影响向量路。

---

### 技术点 D：为什么融合用 RRF（而不是加权平均 / 学习式融合）

**是什么**：两路结果按 **RRF（Reciprocal Rank Fusion）** 合并：`score = Σ 1/(K + rank)`，K=60，只依赖**排名**。

**为什么**：
- 两路分数量纲不同：向量是余弦相似度（0~1），关键词是 BM25（可到几十），**加权平均会放大数值大的那路**；
- RRF 只关心"在各自榜单里的名次"，天然规避量纲问题；
- **几乎无参数**（只一个 K），稳健、不需调权重、不依赖训练数据。

**为什么不用其他方案**：
- 加权平均：量纲不可比，权重靠拍脑袋，换个数据集就要重调；
- 学习式融合（如给两路打分训练排序模型）：需要标注数据 + 训练管线，当前场景收益不抵成本；
- 结论：RRF 是"性价比最优的融合"，代价是丢掉分数绝对值信息——正好由后面的 Rerank 补回。

**风险**：只靠排名，可能把"分高但名次靠后"的信息丢掉。
**优化**：融合后只取前 candidate_top_k（6 条）进重排，量小才重排得起。

---

### 技术点 E：为什么做 Parent-Child 提升

**是什么**：检索粒度用 **Child 小块**（命中精准），命中后把该块**替换为它所属的 Parent 大块**作为回答依据。

**为什么**：
- 切块粒度矛盾：**块大命中不精准，块小上下文不完整**；
- Child 小块解决"命中"——语义聚焦、召回准；
- Parent 大块解决"上下文"——回答时避免断章取义，章节完整；
- 入库时**只有 Child 块做 embedding**（省向量存储），Parent 块仅存文本，通过 parent_chunk_id 关联，检索命中小块后反查大块。

**为什么不用其他方案**：
- 只用大块：命中粒度太粗，一个章节块可能几百字，和问题相关的可能只有一句话；
- 只用小块：上下文被切碎，"前置条件"这类跨句信息拿不到。

**风险**：提升后的 Parent 块可能很大，撑爆上下文预算。
**优化**：提升时截断到 `parent_evidence_max_chars`（2200 字）；保留命中块的原始分数作为排序依据，不因提升改变排序。

---

### 技术点 F：为什么还要 Rerank（RRF 之后为什么还要精排）

**是什么**：融合后的候选交给一个**可配置的 Rerank 模型**（SiliconFlow BGE-reranker 兼容协议），逐条算"问题 vs 证据"的相关性并重新排序，再截断到 final_top_k。

**为什么**：
- RRF 解决的是"两个榜单怎么合并"，不是"这段证据对当前问题到底多相关"；
- 没有 Rerank，融合后顺序仍受各通道原始打分影响——可能把"关键词撞得多但语义无关"的结果排前面；
- Rerank 是**真正按当前问题**的语义精排，比召回阶段的打分质量高一个量级。

**为什么可配置**：不同业务对"精排要花多少成本、准到什么程度"诉求不同——开关（enabled）、模型、top_n、最低分阈值（rerank_min_score）全部配置化，可灰度、可关闭。

**为什么不用其他方案**：
- 不重排：融合顺序不够准，Top-5 里可能混入噪音；
- 把重排提前到召回：召回阶段候选量大，重排成本太高。

**风险**：Rerank 是外部调用，可能超时/失败/变慢。
**优化**：Rerank 失败降级为跳过（直接使用融合结果），**不因重排挂掉而中断回答**；重排结果按最低分阈值过滤低质候选。

---

### 技术点 G：证据闸门 —— 召回后先滤低质

**是什么**：两路结果进融合前先各自过滤：
- 向量路：相似度 < `min_vector_similarity`（0.55）直接丢弃；
- 关键词路：取最高分 × `keyword_score_ratio`（0.35）作为下限，低于下限丢弃（相对阈值，自适应不同查询）。

**为什么**：
- 双通道并行召回会带进噪音（语义偏、但关键词撞上的无关块）；
- 融合前过滤，避免低质候选混进融合、污染最终排序；
- 关键词用**相对阈值**而非绝对阈值：BM25 分数随查询变化大，相对最高分的比例更稳。

**风险**：阈值太严会把真证据滤掉（召回变低），太松噪音多（精度变低）。
**优化**：两个阈值都是配置项，用离线对比实验定，坏 case 可调。

---

### 技术点 H：证据不足怎么办 —— Corrective Retrieval

**是什么**：第一轮检索后如果所有子问题都没有有效证据，自动**改写查询重查**一次（`corrective_retrieval_max_rounds = 1`），仍不足则返回"资料不足"兜底。

**为什么**：LLM 生成的查询是软性的，第一轮可能查不准确（词用错、太啰嗦、过滤加错）；给一次"换说法重查"的机会，成本可控（最多一轮）收益明显。

**为什么不用其他方案**：
- 无限重查：成本失控，还可能越查越偏；
- 直接放弃：浪费了一次可能的挽救。

**风险**：改写后仍查不到，用户得到"资料不足"。
**优化**：兜底文案明确说明"没有检索到足够证据"，而不是空回复；Prompt 同时硬约束模型"严格基于证据，不编造"，从根上防幻觉。

---

### 技术点 I：切块为什么多种策略

**是什么**：入库切块支持多种策略——结构切块（按文档章节结构切，保留 section_path/canonical_path/条目序号）、递归切块（按长度递归切，默认 800 字 + 120 overlap）、语义切块（jieba 分词 + Jaccard 相似度合并相邻相似块）。

**为什么**：
- **结构切块**：文档有明确层级（章节/步骤），按结构切出来的块自带路径信息，检索时可做章节过滤、回答时引用带路径——这是知识库问答特有的优势；
- **递归切块**：无结构文档的兜底，按长度 + overlap 保证边界不过度切断语义；
- **语义切块**：相邻块相似度高就合并，避免把一个话题切成两半。

**为什么 overlap（120 字）**：相邻块的边界常有"承上启下"的句子，overlap 让边界内容在前后两块都出现，避免检索时因切分边界漏掉关键句。

**风险**：不同文档适合不同策略，选错策略切块质量差。
**优化**：策略配置化、可对单文档选策略；向量化失败批有零向量兜底，不中断入库。

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"为什么双通道"出发
- **第一层**：为什么不用纯向量检索？
  - 答：企业文档精确信息密集（型号、编号、专有名词），纯向量会漏精确匹配。
- **第二层**：精确匹配为什么不能靠向量解决？
  - 答：向量把文本编码成语义，同义表达能召回，但"R6.2"这种型号和别的词在语义上不显著区分，容易被淹没；BM25 对精确词命中是强项。
- **第三层**：两路结果怎么合？分数能直接加吗？
  - 答：不能。向量是余弦（0~1），BM25 可到几十，量纲不可比。用 RRF 只按排名合并，规避量纲。

### 追问链 2：从"为什么用 RRF"出发
- **第一层**：RRF 是什么？
  - 答：按排名倒数融合：score = Σ 1/(K+rank)，只看名次不看分数。
- **第二层**：为什么不用加权平均？
  - 答：分数量纲不可比，加权会被数值大的那路主宰，权重还难调。
- **第三层**：RRF 的缺点是什么？谁补？
  - 答：丢分数绝对值信息，融合顺序仍不够准。由后面的 Rerank 补——召回靠广、精排靠准，分层设计。

### 追问链 3：从"Parent-Child"出发
- **第一层**：为什么不做成单一粒度？
  - 答：块大命中不精准，块小上下文不完整，单一粒度顾此失彼。
- **第二层**：小块命中后提升大块，排序会不会乱？
  - 答：不会。提升只换内容，**保留命中块的原始分数**作为排序依据，只截断长度防超预算。
- **第三层**：为什么只对 Child 做 embedding？
  - 答：省向量存储和计算。Parent 只存文本，通过 parent_chunk_id 反查，检索命中小块后取回大块。

### 追问链 4：从"召回率数字"出发
- **第一层**：72% → 91% 是怎么测出来的？
  - 答：离线对比实验：同一批标注问题，分别用纯向量、双通道融合、融合 + Rerank 三种策略跑，逐条算 Top-5 召回准确率，对比出报告选最优。
- **第二层**：这个实验在代码里怎么支撑？
  - 答：有对比实验框架——定义多组检索策略（rerank 开/关、top_k、权重），对每个标注样本逐条检索 + 评分，聚合出各策略均分并选赢家。
- **第三层**：91% 之外还有多少提升空间 / 瓶颈在哪？
  - 答：剩余误差主要在"查询本身不清晰"和"文档切块边界"。方向是查询改写优化、切块策略调参、以及重排模型升级——这些都是可评测、可迭代的。

### 追问链 5：从"通道挂了"出发
- **第一层**：ES 挂了你怎么办？
  - 答：关键词路降级为 PG 内关键词模糊匹配，回答不中断，但精确匹配质量下降。
- **第二层**：向量路挂了呢？
  - 答：向量检索失败返回空结果，只走关键词路；embedding 调用失败同理降级。
- **第三层**：怎么知道哪路在挂？
  - 答：每路有通道级统计（召回数、失败数、耗时），监控看得到"哪路通道开始频繁失败"，配合全链路 Trace 定位单轮降级。

## 5. 极端情况处理（怎么办层汇总）

| 场景 | 怎么办 |
|------|--------|
| ES 宕机 / 超时 | 关键词路降级为 PG 模糊匹配；单通道 5s 超时降级，不影响向量路 |
| 向量路失败 / embedding 调用失败 | 返回空结果，只走关键词路 |
| Rerank 失败 / 超时 | 降级跳过，直接使用融合结果，不中断回答 |
| 证据不足（第一轮没查对） | Corrective Retrieval：改写查询重查一次，仍不足返回"资料不足" |
| 双通道都空 / 都被闸门滤掉 | 明确返回无证据兜底文案，不硬编 |
| 候选噪音多 | 证据闸门（绝对/相对阈值）先滤，融合后再 Rerank 精排 + topk 截断 |
| Parent 块太大 | 截断到 parent_evidence_max_chars，保留命中块原始分数排序 |
| 上下文超预算 | Prompt 组装预算控制：超限降预算裁剪、重复引用不重复塞原文 |
| 向量化入库批量失败 | 零向量兜底，不中断入库流程，可重跑（UPSERT 幂等） |
| 量化数字被追问口径 | 见下方隐患清单 |

## 附：面试前必查的隐患

| 隐患 | 说明 | 应对 |
|---|---|---|
| "72% → 91%"测量口径 | 简历数字必须能复现口径 | 讲清：对比对象（纯向量 vs 双通道+RRF+Parent-Child+Rerank）、指标（Top-5 召回准确率，即标准证据是否在 top5）、数据集来源、是否含 rerank。答不出就弱化 |
| 向量与元数据跨库 | PGVector 存向量、业务元数据在 MySQL，会不会不一致 | 主动讲"入库 UPSERT 幂等、文档删除多级清理（PG/ES/Neo4j/DB 级联）"，展示一致性考虑 |
| RRF 的 K 值怎么定的 | 文档写 K=60 | 答：RRF 对 K 不敏感，60 是常见默认；真正敏感的是"融合后候选量"，由 candidate_top_k 控制 |
| 为什么不用向量数据库 | 面试官可能认为"正经系统该用 Milvus" | 答规模决定选型：当前量级 PG 够用且支持过滤一体化；接口已隔离，可迁移专用向量库 |
| rerank_min_score 默认 0 | 配置默认 0 表示不按分过滤，只排序 | 别吹"按最低分过滤"是默认行为；是"可配置、默认关闭" |
