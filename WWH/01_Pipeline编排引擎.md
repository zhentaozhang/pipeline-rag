# 主题一：泛型 Pipeline 对话编排引擎 —— 面试深挖分析

> 基于"业务问题 → 技术方案 → 设计原因 → 实现方式 → 遇到问题 → 优化方案 → 极端情况处理"链路。
> 每个技术点按「是什么 / 为什么 / 怎么办」三层组织，代码锚点均经 codegraph 核实。

---

## 1. 项目背景

### 业务场景
这是一个面向企业内部知识库的 RAG 对话系统。用户问一句话，系统要决定"这个问题该怎么回答"并执行。问题性质差异极大：
- **文档知识问答**（查内部手册、流程、政策）——走知识检索；
- **开放闲聊**（非知识类）——直接聊天；
- **文档歧义**（几份文档都像）——先反问澄清；
- **复合问题**（对比 A 和 B）——拆子任务（衔接主题二）；
- **章节定位**（"第 3 步怎么配"）——走图谱导航。

### 原来的方案有什么问题
如果不做编排，直接"问什么答什么"，会出现三类问题：
- **路径不匹配**：开放闲聊被拉去检索知识库，返回一堆无关文档；知识问题被当闲聊糊弄过去。回答质量取决于"碰运气"；
- **成本失控**：每个问题都走全套（改写 + 检索 + 生成），简单问题也付出全套 LLM 开销；
- **无法治理**：决策逻辑散落在业务代码里，无法单独观测"这一步判断对不对"、无法单独降级、无法测试。

### 为什么需要重新设计
需要把"如何决策回答路径"抽出来，做成**显式、可观测、可短路**的一层：
- 决策本身要便宜（不能决策比回答还贵）；
- 决策要能复用（加新模式 = 加一个判断，不动核心逻辑）；
- 决策要能被追踪（答错了要能查"是决策错了，还是执行错了"）。

> 一句话背景叙述（面试开场用）：
> "业务方想要一个能区分场景的问答系统：知识问题检索、闲聊直接聊、歧义先反问。如果不用编排，就得在每个问题入口写一堆 if-else 判断走哪条路，没法测、没法降级、还贵。所以我们做了一个泛型编排引擎：把一次请求拆成 10 个顺序执行的 Stage，每个 Stage 返回继续 / 跳过 / 终止信号，已经确定答案路径的请求直接短路，后面的阶段全都不跑。这样决策逻辑集中、可观测，而且大多数简单问题根本不用走完整链路。"

## 2. 整体架构

### 编排拓扑（10 个 Stage 快照）
```
[Pipeline 泛型编排层]  ctx: PrepareContext → plan: ExecutionPlan
 1  HistoryBuilding      历史上下文构建（摘要 + 最近窗口 → 规划用上下文）
 2  TimeSensitivity      时间敏感检测（"本月新政策" → 注入今天日期）
 3  Guardrail            企业护栏（涉密/越权 → TERMINATE 拒绝）
 4  Validation           硬校验（RAG 未开 / 文档模式缺文档ID → 抛错）
 5  OpenChatShortcut     仅开放聊天模式跑，进来即 TERMINATE
 6  IntentClassify       仅自动路由模式跑；判"开放提问" → TERMINATE
 7  QueryRewrite         查询改写；无需改写 → SKIP
 8  KnowledgeRouting     知识路由（域→主题→文档）；歧义 → TERMINATE 澄清
 9  NavigationAnalysis   文档章节导航分析 → 决定图谱/检索模式
10  FinalPlanBuilding    汇总所有决策 → TERMINATE 产出 ExecutionPlan
```

### 三态信号
```
CONTINUE   正常完成，携带新上下文交给下一 Stage（大多数）
SKIP       Stage 已执行，主动"无事可做"，不更新上下文，管道继续走（仅查询改写用）
TERMINATE  立即终止整条管道，直接返回结果（四处短路 + 最后收口）
```

### 关键数据流
```
用户提问
  → 入口：加载记忆 → 构建 PrepareContext
  → Pipeline.run(ctx)：按序执行 10 个 Stage，遇 TERMINATE 提前返回
  → 得到 ExecutionPlan（模式 + 子问题 + 目标文档 + 历史）
  → 后置：Supervisor 任务分解（可选，衔接主题二）
  → 执行器按 plan.mode 分发（检索/开放/多智能体）
```

### 架构核心：为什么短路是延迟的第一杠杆
- 四个 TERMINATE 点全部选在"答案路径已唯一确定"处：护栏（必须停）、开放聊天（无需检索）、意图判开放（无需路由）、路由遇歧义（避免猜错文档白跑一轮检索）；
- 每短路一次，就省掉后续所有 Stage 的 LLM 调用和网络往返——这是"平均延迟降低约 35%"的主要机理（数字口径见隐患清单）。

> 架构叙述锚点：
> "编排层本身不做重活，只串起判断；重活（改写、路由、检索决策）都在各 Stage 内部。一个请求到底走几步，由三态信号和条件声明共同决定——同一个入口，可能 3 步出结果，也可能走满 10 步。"

## 3. 核心技术方案拆解

### 技术点 A：为什么自研泛型 Pipeline（而不是 if-else / LangGraph / LCEL）

**是什么**：`Pipeline[C, R]` 泛型管道抽象，接受上下文 C 返回结果 R；Stage 是抽象基类，暴露 `process(ctx) -> StageResult`；`StageResult` 携带三态信号 + 新上下文 + 最终结果；Pipeline 按序执行并解释信号。

**为什么**：
- 决策逻辑从业务代码里抽出来，成为一份**可读、可单测、可追踪**的结构；
- 每个 Stage 是独立单元：可 mock、可降级、可独立记录耗时；
- 泛型化（C→R）让这套抽象**不绑定 LLM 概念**，检索、路由、护栏都能复用同一管道。

**为什么不用其他方案**：
- **if-else 硬编码**：模式多了之后改动要动多处、无法单独测试，判定路径不可见、不可追踪；
- **LangGraph / LangChain LCEL**：它们是 Agent 编排框架，强于循环、多 Agent 协作图；但主编排链路是"线性 + 少量短路"结构，引框架反而带来运行时心智负担。Supervisor 模块（主题二）确实用了 LangGraph——**主编排用轻量自研，复杂 Agent 图用框架，各取所长**；
- **状态机**：状态机强在"状态流转合法性"，但 Pipeline 关注的是"按序决策 + 短路"，语义不匹配。

**风险**：自研要自己保证"所有路径都能产出结果"（TERMINATE 缺 plan 时抛异常兜底）。
**优化**：管道只做控制流，重活下沉 Stage；新增模式 = 加 Stage / 改条件，不动核心。

---

### 技术点 B：三态信号设计 —— CONTINUE / SKIP / TERMINATE 的边界

**是什么**：每个 Stage 返回三种信号之一，由 Pipeline 统一解释。

**为什么用三态而不是两个**：
- 两个信号不够：`SKIP` 和 `TERMINATE` 语义必须分开——
  - **TERMINATE** = 整条管道到此为止（短路）；
  - **SKIP** = 本 Stage 没事做，但管道照常继续。
- 用异常/魔法值模拟控制流会污染代码，三态让"正常推进"与"提前终止"在类型层面区分开。

**SKIP 的真实使用（容易被面试官追问的点）**：全项目只有**查询改写**会返回 SKIP——LLM 判断问题已经足够清晰、无需改写时，返回 SKIP，**不更新上下文**，管道继续走。下游所有读改写结果的地方都做了"改写 or 原问题"兜底，所以跳过是安全的。

**为什么由 Stage 返回信号、由 Pipeline 统一解释**：控制流集中一处，每个 Stage 不关心"我在第几个、前后是谁"，可复用、可重排。

**风险**：SKIP 和"条件跳过"容易被人搞混（见技术点 D）。
**优化**：信号语义在类型上固定，误用靠类型检查拦截。

---

### 技术点 C：10 个 Stage 的粒度怎么定的

**是什么**：一次请求拆成 10 个 Stage，边界落在"一次外部调用或一个明确决策"。

**为什么是 10 个这个粒度**：
- **太粗**：无法定位"慢在哪一步"，无法独立复用（如护栏单独测）；
- **太细**：请求被拆出大量内部调度开销，且难以维护；
- 10 个 Stage 恰好每次都是**真实决策点**（LLM 调用、检索、校验）。

**为什么顺序这么排**：便宜的判断在前（护栏、时间检测、模式校验），贵的判断在后（改写、路由、导航）——**让绝大多数短路发生在最前面，避免为一次可能被拦下的请求花大钱**。

**风险**：Stage 序号调整会影响整条链路语义。
**优化**：顺序由组装声明控制，调整只改一处；每个 Stage 独立可测。

---

### 技术点 D：条件执行 `.when()` —— 外部跳过 vs 内部让行

**是什么**：Pipeline 组装时给部分 Stage 挂条件（`.when()`），条件不满足时**在进入 Stage 之前**直接跳过，Stage 内部逻辑完全不执行。

**为什么要条件执行**：不是每个 Stage 对每个模式都适用——意图分类只在自动路由模式跑、知识路由只在需要选文档的模式跑、开放聊天短路只在开放聊天模式跑。用条件声明把"该不该跑"从 Stage 内部提到组装层。

**与 SKIP 的区别（面试必辨）**：
- `.when()` 是**外部跳过**：Stage 根本没执行；
- `SKIP` 是**内部让行**：Stage 已执行，主动宣布无事可做。

**风险**：条件写错 → Stage 该跑不跑 / 不该跑乱跑。
**优化**：条件是纯函数，可单测；Trace 里能看到每个 Stage 是否被条件跳过。

---

### 技术点 E：编排与执行解耦 —— ExecutionPlan 契约

**是什么**：编排层不直接回答任何问题，只产出一份 **ExecutionPlan**（执行模式 + 子问题列表 + 目标文档 + 历史摘要 + 是否时间敏感 + 是否需澄清），交给执行器按 `mode` 分发。

**为什么**：决策与执行解耦后——
- 新加一种回答方式（如图谱导航路径）**不碰编排**，只注册新执行器；
- 同一份计划可被不同执行器消费，可单独 mock 执行器测编排，反之亦然；
- 决策留痕：答错了能查"是计划错了（编排），还是产出错了（执行）"。

**风险**：计划与执行器模式枚举需同步演进，漏注册会走不到执行器。
**优化**：执行器按模式注册表分发；模式枚举集中管理。

## 4. 重点准备追问链（三层连问）

### 追问链 1：从"为什么自研，不直接用现成框架"出发
- **第一层**：编排层为什么不用 LangGraph？
  - 答：主编排是"线性 + 少量短路"，自研泛型 Pipeline 一百多行就够，轻、直白、不绑定 LLM 概念。
- **第二层**：那你们系统里完全没有 LangGraph 吗？
  - 答：有。Supervisor 多智能体分解那块用了 LangGraph（主题二）。原则是：**简单的用轻量自研，复杂的 Agent 图用框架**，各取所长。
- **第三层**：自研 Pipeline 最怕出什么问题？
  - 答：最怕"所有 Stage 都 CONTINUE 却没人产出计划"。所以 Pipeline 有防御性兜底：跑完没结果抛异常暴露组装错误，正常场景最后一个 Stage 必然 TERMINATE，不会走到。

### 追问链 2：从"SKIP 和条件跳过"出发
- **第一层**：SKIP 是干嘛的？
  - 答：Stage 已执行后宣布"无事可做"，不更新上下文，管道继续走。全项目只有查询改写会用——问题无需改写时跳过。
- **第二层**：那"条件不满足不跑这个 Stage"是 SKIP 吗？
  - 答：不是，那是 Pipeline 层的 `.when()` 条件，在**进入 Stage 前**就跳过，Stage 根本不会执行。SKIP 是 Stage **内部**返回的。
- **第三层**：跳过改写后，下游拿什么用？
  - 答：下游一律"改写 or 原问题"兜底，改写为空时用原问题继续，不会 NPE 也不会丢语义。

### 追问链 3：从"短路点怎么选"出发
- **第一层**：哪几个 Stage 会短路？
  - 答：护栏拦截、开放聊天、意图判开放、路由遇歧义四处 TERMINATE，加上最后收口的计划构建。
- **第二层**：为什么这里短路、那里不短路？
  - 答：标准是**这一步已能确定最终答案路径，后续 Stage 不改变结论**。反例：查询改写不短路，它不改变路径、只优化查询质量。
- **第三层**：短路会不会误伤？知识问题被当开放聊天短路了怎么办？
  - 答：会，这是最大的风险。缓解：护栏只拦确定违规；意图分类设置信度阈值，不确定走默认知识路径；误判通过 Trace + 采样评估发现后调阈值/改 prompt。

## 5. 极端情况处理（怎么办层汇总）

| 场景 | 怎么办 |
|------|--------|
| 所有 Stage 全 CONTINUE 但无结果 | Pipeline 抛异常暴露组装错误（防御性，正常不触发） |
| TERMINATE 但未带 plan | 同样抛异常——表明该 Stage 实现 bug |
| Stage 内 LLM 调用失败（改写/意图分类） | 返回 SKIP / 兜底原问题，管道不中断 |
| 检索类 Stage（知识路由）失败 | 降级到朴素路径，保证"总有一个答案路径" |
| RAG 未启用 / 文档模式缺文档 ID | ValidationStage 硬校验直接抛错终止 |
| 护栏误杀正常问题 | 规则可配置、可灰度，采样评估发现后调整 |
| 意图分类把知识问题判成开放聊天 | 置信度阈值 + 默认走知识路径，Trace 回溯单轮决策 |
| 同一会话并发重复请求 | 入口 Redis 租约锁 + 进程内注册表双保险 |
| 延迟定位 | 每 Stage 独立耗时随 Trace 落库，单轮可查"哪步最慢/是否短路" |
| 新增一种回答模式 | 加 Stage 或改条件 + ExecutionPlan 加字段 + 注册执行器，不碰核心 |

## 附：面试前必查的隐患

| 隐患 | 说明 | 应对 |
|---|---|---|
| 代码注释编号不一致 | 各 Stage 文件头注释写 `Stage X/11`，但编排器实际组装 **10 个**（疑似历史遗留） | 被翻代码追问就答"主线编排目前组装 10 个，注释是早期设计遗留，第 11 个一度规划后来拆到了 Pipeline 后置（Supervisor 分解）" |
| "35% 延迟降低"缺口径 | 简历写了约 35%，需准备测量口径 | 想清楚：对比对象（短路前 vs 短路后？基线版本 vs 现版本？）、测量点（首字延迟/总耗时/P50 或 P95？）、样本量。答不出就弱化为"主要靠短路省掉后续 Stage 的 LLM 调用" |
| Supervisor 不是第 11 个 Stage | 任务分解是 `prepare()` 收尾的 post-processing | 别把 Supervisor 说成 Stage，它是管道后处理，与 Pipeline 分层 |
